## KV cache 为什么要分页

Lab 02 的连续缓存给每个请求一段容量固定的张量。如果一个请求最多允许存 64 个位置，眼下只用了 7 个，留给它的其他位置仍然占用容量。多个请求长度悬殊，而且随生成过程逐步增长，就会同时出现每个请求内部的闲置空间，以及池中空闲空间分散在不同位置的情况。[Lab 02 的缓存布局](lab02_cache.md#历史-kv-为什么能复用)、[PagedAttention 论文第 4 节](https://arxiv.org/html/2309.06180)

把一个共享池切成同样大小的 block 后，请求按块获得容量。逻辑 token 位置依然是连续的 `0, 1, 2, ...`，相邻的逻辑块可以落在不相邻的物理块里。比如只剩物理块 `1` 和 `3` 空闲时，一个需要两块的请求仍然可以分配成功。若恰好只分配覆盖请求长度所需的块，尾块最多闲置 `block_size - 1` 个 slot。这是块粒度带来的内部碎片。分配与归还有多少块可用，和共享池本身分配多少物理内存是两个量。Lab 05 将先建立共享张量池，再用这些块 ID 管理其中的使用权。[PagedAttention 论文第 4.2 节](https://arxiv.org/html/2309.06180)

## 三个容易混淆的量

| 量 | 由谁管理 | 示例 |
| --- | --- | --- |
| 物理块 ID | `BlockPool` 管理全池中每个 ID 的可用状态 | 共 4 块时，合法 ID 是 `0..3` |
| 逻辑保留长度 | `BlockTable` 维护一个请求已保留的 token 范围 | `reserved_tokens=7` 时，合法逻辑位置是 `0..6` |
| 每层已写入长度 | 后续 `PagedKV` 维护实际已经写入的 K/V 前缀 | 已保留 7 个位置时，某层可以只写了前 5 个 |

例如 `block_size=4` 时，`reserve(7)` 需要 2 个物理块，共有 8 个物理 slot，但逻辑位置 7 仍未保留。把 `reserve(7)` 再增长到 `reserve(8)`，只需扩大逻辑范围。到 `reserve(9)` 才需要第 3 个块。需要的总块数是 `ceil(total_tokens / block_size)`，可以用整数算式 `(total_tokens + block_size - 1) // block_size` 求出。

## 手算逻辑位置到物理 slot

设 `block_size=4`。物理块 `0`、`2` 正被占用，这个请求按逻辑块顺序取得物理块 `[3, 1]`。分配器也可以给出相反顺序，关键是每个表项确定后保持稳定。对逻辑位置 `p`，先做 `divmod(p, block_size)` 得到逻辑块号和块内偏移，再从表中查物理块号。扁平 slot 等于 `物理块号 × block_size + 块内偏移`。

| 逻辑位置 `p` | 逻辑块 | 块内偏移 | 物理块 | 扁平 slot |
| ---: | ---: | ---: | ---: | ---: |
| 2 | 0 | 2 | 3 | 14 |
| 3 | 0 | 3 | 3 | 15 |
| 4 | 1 | 0 | 1 | 4 |
| 5 | 1 | 1 | 1 | 5 |
| 6 | 1 | 2 | 1 | 6 |

因此 `slots(2, 5)` 返回 `(14, 15, 4, 5, 6)`。结果的顺序就是请求的逻辑 token 顺序。将块表或 slot 按物理地址排序会改变逻辑位置与历史 K/V 的对应关系。分页也无需改变 `start_pos`、RoPE 或因果掩码里的逻辑位置。

## 实现顺序与验收

### 先实现 `BlockPool`

开始时，每个合法物理 ID 都是空闲的。`allocate(n)` 要先确认有足够的块，再一次提交分配。剩 1 块时申请 2 块，应抛出 `CapacityError`，原来那 1 块依旧空闲。`free(block_ids)` 接受 `Iterable`，可以先把这批输入读成一个序列，再整批检查重复、越界和当前是否已分配。即使前几个 ID 合法，只要有一个非法，整个归还操作就报错，池状态原样保留。

### `BlockPool` 代码复盘

第一版用布尔表记录各物理块是否已分配，再用 `size` 缓存计数。常规容量不足时，`allocate` 会在修改之前抛错。`free` 用临时集合记录本批见过的 ID，整批验证完成后再归还。这也适用于只能遍历一次的生成器。实测生成器在提供第一个 ID 后抛异常，池的状态仍保持原样。

- **先处理负数边界。** `BlockPool(3).allocate(-1)` 返回 `[]`，但 `size` 减为 `-1`，`free_count` 变成 `4`。随后 `allocate(4)` 会通过容量检查，只返回 3 块，破坏了成批分配的约定。负 `count` 应在检查容量和改变状态之前拒绝。`allocate(0)` 已表现为空操作。构造时也应拒绝负容量，避免一开始就出现负的 `free_count`。
- **一种简化是只维护空闲 ID 集合。** 用 `len` 得到空闲数，分配前检查数量，随后取出所需 ID。校验归还时先确认 ID 合法，再判断它是否已经在空闲集合里。整批验证通过后统一归还。这样省去 `size` 和布尔表之间的同步，也省去每次分配时从头扫描布尔表。现有接口和测试允许分配器选择具体 ID 顺序，`BlockTable` 会按收到的顺序记录映射。保留布尔表也可以，至少用 `_allocated_count`、`is_allocated`、`block_ids` 把各变量的含义写清楚。

第二版改为 `free_ids` 列表加 `allocated` 布尔表，`free_count` 直接取列表长度。独立运行 1000 轮分配、归还和非法操作，两个结构中的状态与参考集合一致，非法批量归还也保持了原状态。复查时还发现以下几点。

- 当时 `allocate(-1)` 返回空列表，池状态保持原样。`BlockPool(-1)` 仍然能构造，得到 `capacity=-1`、`free_count=0`，从构造起就违反计数不变量。
- `free_ids[:count]` 和 `free_ids[count:]` 都会复制列表。用 `F` 表示分配前的空闲数，这两次复制共涉及 `F` 项。`return list(ret)` 又复制一次已切出的独立列表，可以直接返回切片结果。
- 如果沿用列表和布尔表，可以把空闲列表当栈，从尾部逐项取出，分配一个块时就无需搬剩余的空闲 ID。现有 Lab 允许任意分配顺序。仍需保证对每个合法 ID，它恰好处于空闲列表或已分配状态之一，空闲列表里各 ID 唯一。

当前版本从列表尾部 `pop()` 所需的 ID，避免分配时复制整份空闲列表。实测非法构造容量和负 `count` 都会被拒绝，`allocate(0)` 为空操作，真实容量不足也不会改变池状态。非法参数和真实容量不足目前都抛 `CapacityError`。后续如果调用方需要据此判断请求是否值得等待，建议用 `ValueError` 表示非法参数，把 `CapacityError` 留给合法申请缺少空闲块的情况。

### 再实现 `BlockTable`

- 初始化时逻辑保留长度为 `0`，映射表为空。内部要能在尾部追加，公开的 `block_ids` 按接口返回 `tuple`，调用方可以读取映射顺序。
- `reserve(n)` 用总长度算还缺几个块，向池申请差额。新块按逻辑顺序接到表尾，已经建立的映射保持稳定。申请失败时，表和逻辑保留长度都保持原样。
- `slots(start, count)` 先验证整个 `[start, start + count)` 是否落在保留范围，再按逻辑顺序做地址翻译。注意 `count` 是数量，和 Lab 02 的切片一样，需要用 `start + count` 算右端点。
- `release()` 归还当前表拥有的全部块，并清空表和保留长度。对同一张已释放的表再调用一次时，它已经没有块需要归还。与之对应，直接对池重复 `free` 同一批 ID 是非法操作，池会报错。

手推 `reserve` 的提交顺序。设 `block_size=4`，请求已保留 7 个位置并持有 `[3, 1]`，池里没有空闲块。分别从这份状态出发：

| 调用 | 还需几个块 | 应有结果 |
| --- | ---: | --- |
| `reserve(5)` | 0 | 保持保留长度 7，沿用旧映射 |
| `reserve(8)` | 0 | 保留长度变为 8，沿用旧映射 |
| `reserve(9)` | 1 | 申请失败，保留长度仍为 7，表和池状态原样保留 |

`total_tokens` 表示目标总长度。所需的总块数向上取整，减去 `len(block_ids)` 才得到这次需要申请的块数。先向池拿到差额，再把 ID 接到表尾并提交新的保留长度。`slots()` 用保留长度检查范围，所以第一个状态下的 `slots(7, 1)` 应报错，而 `reserve(8)` 成功后同一个位置就可以翻译为物理 slot `7`。

### `BlockTable` 代码复盘

第一版已通过跨页翻译用例，它验证了非连续物理块可以按逻辑顺序访问、扩容失败不改变状态、正常释放可重复调用。当时完整复跑的随机用例首次失败在从空表 `reserve(16)`，实际保留长度为 `12`。

| 复现 | 原因与建议 |
| --- | --- |
| `block_size=4` 时 `reserve(4)` 已占一块，但 `reserved_tokens == 0`，`release()` 后块仍未归还 | `T % B` 的余数可以是 0，最后一块此时正好填满。通过 `reserved_tokens == 0` 判断是否有资源也会掩盖这类错误，释放应以表里实际持有的块为准。 |
| `reserve(7)` 后再 `reserve(5)`，保留长度降为 5 | 更小的目标仍然改写了末块计数。`reserve` 应保证成功后长度等于 `max(旧长度, 目标长度)`。 |
| `slots(4, -1)` 返回 `()`，`block_size=0` 到 `reserve` 时才报除零 | 地址翻译应先拒绝负 `count`，构造时可以明确要求正的 `block_size`。 |

建议直接保存一个逻辑保留长度，配合按逻辑顺序保存的物理块 ID 列表。扩容用长度计算块数差额，先成功分配，再追加 ID 并更新长度。同一块内增长也需要更新长度。`slot_counts` 中间项可由整页容量推出，减少一份需要同步的状态可以避开类似的余数边界。

`block_ids` 返回 `tuple` 作为外部快照很合适。第一版在 `slots` 循环里每次访问 `self.block_ids` 都会复制整张表。当前版本索引内部列表，保留了外部的不可变快照。

当前实现保留 `slot_counts`。末页占用数用 `T - (持有块数 - 1) × B` 计算。对已保留的正长度，末页占用数在 `1..B`。例如 `T=4, B=4` 时末页占用 4 项，余数为 0 表示恰好填满。更小或相同的目标在计算前直接返回。接下来实现调度器，分页池将在 Lab 05 通过准入和回收回调接进引擎。[Lab 04](lab04_scheduler.md)
